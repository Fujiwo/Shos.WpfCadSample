## 指摘の詳細

### 1. ビルド・テストのコマンドがバックスラッシュ区切りで、実行環境の指定がない（中）

- 場所：§0（17行）、§11 の完了条件（197–198行）。
- 根拠：リポジトリ指示（`copilot-instructions.md` 59–61行）は、コマンドを `/` 区切り（`dotnet build Source/Shos.WpfCadSample/Shos.WpfCadSample.slnx`）で書き、Windows の `dotnet`（WSL からは `dotnet.exe`）で実行するとしています。承認済みの実装計画書（3.2）とテスト計画書（2.3）も同じ書き方に改められました。このプロンプトだけがバックスラッシュ区切りで、bash ではパスが壊れます。WPF のプロジェクトは Linux の `dotnet` ではビルド・テストできません。
- 影響：Claude Code（WSL）でこのプロンプトを実行すると、各段階の完了条件の確認が、コマンドの文字どおりの実行で失敗します。
- 改善案：17、197、198行のコマンドを `/` 区切りにし、「Windows の `dotnet` で実行する（WSL からは `dotnet.exe`）。実行できない場合は、確認できなかったことを報告し、完了としない」を §0 に加えてください。

### 2. 実装の段階が、承認済みの実装計画書と食い違う（中）

- 場所：§0（17–22行）。
- 根拠：§0 は「次の順に段階的に進め」として 5 段階（骨組み → Models → ViewModels / Controllers → Views → クリップボード・設定・仕上げ）を指定しています。承認済みの実装計画書は、これを 10 段階（I-1〜I-10）に細分化し、順序も一部異なります（例：クリップボードと EMF の `Infrastructure` は I-7 で Views より先、設定の保存は I-4・I-6 で Views より先）。13行は「承認済み仕様書と設計書を唯一の詳細仕様とする」としていますが、実装計画書とテスト計画書の位置づけ（段階、完了条件、手動テスト）には触れていません。
- 影響：エージェントが、プロンプトの 5 段階と実装計画書の 10 段階のどちらに従うか、段階ごとの完了条件（実装計画書 3.2 の C-1〜C-6、テスト計画書の段階ごとのテスト群）をどう扱うかで迷います。
- 改善案：§0 を「段階、順序、完了条件は、承認済みの実装計画書とテスト計画書に従う（5 段階は、その大枠を示す）」とし、承認済み文書の優先順位（仕様書・設計書 → 実装計画書・テスト計画書 → このプロンプトの要件の要約）を明記してください。

### 3. 曖昧な点の扱いが、承認済み文書の変更手順と食い違う（中）

- 場所：§0（15行）。
- 根拠：15行は「曖昧な点は、合理的な既定値を選んで `Source\README.md` の『設計判断』節に理由を添えて記録する。ユーザーの確認が必須な場合のみ質問する」としています。一方、リポジトリ指示は「承認済みの計画から大きく外れる場合は、計画を更新して承認を得る」とし、承認済みの実装計画書 9 章は、承認を要する逸脱（主要なクラスの責務、保存形式、仕様の動作の変更など）と、承認を要しない実装の詳細（非公開のメソッド、定数の調整など）を分けています。15行は、この区別なしに README への記録だけで済ませてよいと読めます。
- 影響：仕様の動作や設計の責務に関わる判断を、承認なしに README へ記録するだけで実装してしまうおそれがあります。
- 改善案：15行を「承認済み文書で決まっていない実装の詳細は、実装計画書 9 章の『承認を要しない』範囲に限り、合理的な既定値を選んで README の『設計判断』節に記録する。それ以外（承認を要する逸脱）は、実装計画書 9 章の手順で文書を更新し、承認を得る」に改めてください。

### 4. 「図形の種類ごとの `DataTemplate`」の要件が、承認済み文書に対応付けられていない（中）

- 場所：§3（82行）。
- 根拠：§3 は「図形の種類ごとに `DataTemplate`（`Line`、`Ellipse`、`Rectangle`、`Polyline`、`Polygon`、`Path` など）を用意する」と求めています。承認済みの設計書は、図形を `ShapeToGeometryConverter` で `StreamGeometry` へ変換し、`Path` で描く方式（5.7）としていますが、`DataTemplate` を種類ごとに用意するかどうかは書かれていません。仕様書の F-02 は「設計書で扱う」とし、実装計画書・テスト計画書にも `DataTemplate` の記述はありません（`grep` で確認）。
- 影響：設計書どおりに 1 つの `Path` の `DataTemplate` で全図形を描くと、§3 の要件を満たさないと判断されるおそれがあります。逆に、種類ごとに WPF の `Line`・`Ellipse` などを使うと、`Outline` を共通の入力にする設計判断（DD-6、DD-7）と食い違います。
- 改善案：次のどちらかに決めて、関係する文書に明記してください。(a) 設計書に「図形の種類ごとに `DataTemplate` を用意し（`DataType` で選ぶ）、いずれも `Path` と `ShapeToGeometryConverter` で描く。§3 の『`Path` など』に当たる」と追記する（設計書の変更のため、再承認が必要）。(b) このプロンプトの §3 を、承認済みの設計に合わせて「図形の種類に応じた `DataTemplate`（`Path` など）」と書き直す。要件の意図（種類ごとに描き分けられる構成）を保ちつつ設計を変えずに済む (a) を推奨します。

### 5. GUI を操作できない環境での、スモークテストの扱いがない（低）

- 場所：§0（23行）。
- 根拠：「実際にアプリを起動してスモークテスト（図形追加 → 選択 → 移動 → Undo/Redo → 保存 → 読込）を行い、結果を報告する」とありますが、エージェント（WSL 上の Claude Code など）は、WPF の画面を操作できないことがあります。テスト計画書は手動テスト（M-01〜M-22）を「開発者の Windows デスクトップ」で行うとしています。
- 改善案：「エージェントが画面を操作できない場合は、手動テストの手順をユーザーに示して実施を依頼し、結果を進捗記録に記録する。実施されていない項目を合格と報告しない」を加えてください。

### 6. コードビハインドの規則の強さが一致しない（低）

- 場所：§2.2（64行）、§11（199行）。
- 根拠：64行は「`InitializeComponent()` 以外は原則書かない」とし、例外の余地を残しています。199行の完了条件と、リポジトリ指示（`copilot-instructions.md` 50行）は「`InitializeComponent()` 以外のロジックがない」と例外なしです。
- 改善案：64行の「原則」を削り、完了条件と同じ強さにしてください。

### 7. C# の新しい文法の使い方が、リポジトリ指示と食い違う（低）

- 場所：§1（27行）。
- 根拠：27行は「新しい C# の文法（primary constructor、collection expression、`field` キーワード、拡張メンバー、パターンマッチングなど）を積極的に使う」としています。リポジトリ指示（`copilot-instructions.md` 51行）は「明確さが増す場合に、現在の C# の文法を使う」です。「積極的に」は、読みやすさを下げてでも新しい文法を使う方向に読めます。
- 改善案：「新しい C# の文法（…）を、明確さが増す場合に使う」に揃えてください。

### 8. スキルの参照先が `.github\skills\` だけで、複製の確認に触れていない（低）

- 場所：§0（14行）。
- 根拠：14行は `.github\skills\sustainable-code-jp\SKILL.md` を読むよう指示しています。リポジトリ指示（`copilot-instructions.md` 45行）は、`.github\skills\` と `.claude\skills\` の複製を、使う前に比較するよう求めています。Claude Code は `.claude\skills\` の複製を使うため、プロンプトの記述だけでは、比較の手順が抜けるおそれがあります。
- 改善案：「スキルを使う前に、リポジトリ指示に従って `.github\skills\` と `.claude\skills\` の複製を比較する」を加えるか、スキルの参照をリポジトリ指示に委ねる書き方にしてください。
