## 2. どちらを実行していくべきか

### 2.1 それぞれの役割

| | `create-wpf-cad.prompt.md` | 実装計画書・テスト計画書 |
|---|---|---|
| 位置づけ | 要件の出典と、実装の作業ルール（承認の確認、YAGNI、ビルド・テストの方法、進捗の記録）。CAD の実装全体を一度に依頼する入口 | 承認済みの実行手順。段階（I-1〜I-10）、各段階の作業・成果物・完了条件、対応するテストケース |
| 粒度 | 全体を 1 回で依頼する | 段階ごとに区切り、完了条件で確認できる |
| 状態の扱い | 進捗を持たない。実行するたびに全体を最初から読む | 進捗記録と組み合わせて、どの段階まで終わったかを追える |
| 優先順位 | 自らを「段階・順序・完了条件は計画書に従う」と定めている（§0） | 仕様・設計を再定義せず、要件の根拠をプロンプトに置く |

### 2.2 評価

- **プロンプト全体をそのまま再実行するのは推奨しない。** プロンプトは CAD 全体の実装を一度に依頼する形のため、実行するたびに I-1 からの全作業を対象にしてしまう。すでに I-1 の大半（プロジェクト、`Directory.Build.props`、T-ARC、README の骨子）が終わっており、再実行は作業の重複や、完了済みの成果物の作り直しにつながる。また、このセッションではビルドとテストをユーザーが Windows で行うため、一度に多くの段階を進めると、確認できない変更が積み上がる。
- **実装計画書を段階ごとに実行するのが適切である。** プロンプト自身が段階・順序・完了条件を計画書に委ねており、計画書は段階ごとに完了条件（C-1〜C-6）と対応するテスト群を持つ。1 段階ずつ依頼し、段階の終わりにユーザーが Windows でビルド・テストを確認する進め方は、「小さく刻み、常に Green を保つ」方針と、現在の検証の体制（ビルド・テストはユーザーが実行）の両方に合う。
- **プロンプトは、要件の出典と作業ルールとして使い続ける。** 承認の確認、YAGNI、曖昧な点の扱い、ビルド・テストの方法、進捗の記録は、プロンプト（とリポジトリ指示）のルールに従う。

### 2.3 推奨する進め方

1. テスト計画書の付録 A の修正を再承認する（指摘 1。プロンプトの開始条件を満たすため）。
2. I-1 の残り（R-1、R-2、R-6 の試作、パッケージの版の確認、README の理由の追記）を完了する。
3. 以降は「実装計画書の I-2 を実施せよ」のように、段階ごとに依頼する。各段階の終わりに、ユーザーが Windows でビルド・テストし、結果を共有する。
4. 段階を繰り返し依頼する作業を定型化したい場合は、段階を実行するための新しいプロンプト（例：`.github\prompts\run-cad-stage.prompt.md`）を作ることもできる。ただし、現時点では「I-n を実施せよ」の依頼で足りるため、必須ではない。
